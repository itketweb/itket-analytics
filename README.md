# itket-analytics

itket.com 의 GA4 데이터를 **자동으로 모아 보여주는 월별 대시보드**. 사람이 하는 일은 없다.

- **수집**: Apps Script(`apps-script/Code.gs`)가 GA4 에서 30분마다 당월을, 3시간마다 전체 월(빠진 달 포함)을 모은다.
- **실시간**: 화면이 15초마다 Apps Script 웹앱(`?mode=live`)을 확인하고(GA4 호출은 30초 단위, 나머지는 서버 캐시) GA4 Realtime API(최근 30분 접속자·지금 보는 페이지)를 직접 조회하고, 5분마다 당월 수치를 새로 받는다. 깃허브를 거치지 않으므로 지연이 없다.
- **기록 보관**: GitHub Actions 가 3시간마다 수집본을 `data/ga4/`에 커밋(이력)하고 Pages 로 배포한다. 상품·카테고리·게시판 이름은 공개 쇼핑몰 페이지에서 읽어 `data/names.json` 에 캐시한다.
- 화면: 지금 접속 중(실시간) + 연도 탭 → 월 탭(연간 요약 포함). 방문자·세션·페이지뷰·신규 방문자·회원가입·체류시간, 일별/월별 추이, 인기 페이지, 유입(매체·채널·UTM·기기), 고도몰 인기 상품·카테고리·게시판, 전월·전년 대비.
- 진행 중인 달은 "현재까지"로 표시되고 전월과는 같은 기간끼리 비교한다.
- 서버·DB 없음. 수집이 실패하면 이 저장소에 이슈가 자동 등록되고(메일 알림), 화면은 마지막 성공 데이터를 계속 보여준다. 다시 성공하면 이슈가 자동으로 닫힌다.

## 처음 한 번만 (이후 영구 자동)
Google Cloud 콘솔·서비스 계정·JSON 키는 **필요 없다.** GA4 를 볼 수 있는 구글 계정 하나면 된다.

1. **속성 ID 확인** — [GA4](https://analytics.google.com/) → 관리 → 속성 설정 → `속성 ID` (숫자. `G-` 로 시작하는 측정 ID 가 아님).
2. **Apps Script 만들기** — GA4 를 볼 수 있는 구글 계정으로 [script.google.com](https://script.google.com/) → 새 프로젝트.
   - `Code.gs` 내용을 지우고 이 저장소의 `apps-script/Code.gs` 전체를 붙여넣는다.
   - 파일 맨 위 `PROPERTY_ID` 의 `'여기에_GA4_속성_ID_숫자'` 를 1번 숫자로 바꾼다.
   - 왼쪽 `서비스 +` → **Google Analytics Data API** (식별자 `AnalyticsData`) 추가.
3. **권한 승인 + 첫 수집** — 함수 선택에서 `collectAll` → 실행 → 권한 허용(GA4 읽기·드라이브 파일 1개). 한꺼번에 못 채우면 다음 실행에서 이어서 채운다.
   (`API has not been used` 오류가 나면 오류 안의 링크를 눌러 한 번 "사용"만 누르면 된다.)
4. **자동 실행 켜기** — 함수 `setupTrigger` 를 한 번 실행한다 (1시간마다 자동 수집).
5. **웹앱으로 배포** — 오른쪽 위 `배포 → 새 배포 → 유형: 웹 앱` → 실행 계정 **나**, 액세스 권한 **모든 사용자** → 배포 → 나오는 **웹 앱 URL** 을 복사한다.
6. **GitHub Secret 등록** — 이 저장소 Settings → Secrets and variables → Actions → New repository secret: 이름 `GA4_WEBAPP_URL`, 값 = 5번 URL.
7. Actions → **Update Dashboard** → Run workflow. 이후 3시간마다 자동으로 받아 배포한다.
8. 끝. 대시보드는 **https://itketweb.github.io/itket-analytics/** 에서 본다.

> 서비스 계정 방식(`GA4_PROPERTY_ID` + `GA4_SERVICE_ACCOUNT` Secret)도 코드에 남아 있어 쓸 수 있지만, 위 방식이 더 간단해 기본으로 한다.

## 코드를 고쳤을 때 (Apps Script)
`apps-script/Code.gs` 를 고치면 Apps Script 에디터에 붙여넣고 저장한 뒤 **배포 → 배포 관리 → 연필 → 버전: 새 버전 → 배포** 해야 웹앱에 반영된다(주소는 그대로). 수집 항목을 바꿨으면 `SCHEMA` 숫자를 올리면 과거 월도 다시 채워진다. 트리거를 다시 만들려면 `setupTrigger` 실행.

## 전환·페이지 분석·회사 IP 제외 (2026-10-15 추가)
**수집기를 새 버전으로 배포해야 동작한다**: `apps-script/Code.gs` 전체를 Apps Script 에디터에 붙여넣고 저장 → 배포 → 배포 관리 → 연필 → 버전: 새 버전 → 배포. `SCHEMA` 가 3 으로 올라가 있어 다음 `collectAll`(3시간마다)부터 과거 월이 전환·이벤트 항목까지 다시 채워진다(바로 채우려면 에디터에서 `collectAll` 실행, 시간 초과 시 다시 실행). 배포 전에는 대시보드의 전환 카드가 "집계 전", 페이지 분석은 "새 버전이 아님" 안내를 보여 준다.

### 1) 전환 (페이지별·상품별·유입 매체별)
- 이 사이트는 GA4 전환 이벤트를 보내지 않으므로 **전환 = 아래 화면을 본 세션**으로 센다. 정의는 `Code.gs` 의 `CFG.CONVERSIONS` (바꾸면 `SCHEMA` 숫자도 올린다).

| 전환 | 화면 | 비고 |
|---|---|---|
| 견적 요청 완료 | `/dbk/dbk_estimate_complete.php` | 견적 폼 → 확인 → 완료 흐름의 마지막 화면(추정) |
| 회원가입 완료 | `/member/join_ok.php` | 기존 회원가입 집계와 같은 기준 |
| 주문 완료 | `/order/order_end.php` | 고도몰 기본 주문완료 화면(추정) — **실제 주소와 다르면 `CFG.CONVERSIONS` 를 고칠 것** |

- 월 화면의 **전환** 카드: 전환별 건수·전환율·전월 대비, 그리고 **유입 매체 / 채널 / 캠페인 / 랜딩 페이지 / 상품** 별 전환 세션·전체 세션·전환율. 랜딩 페이지·상품은 **방문의 첫 화면** 기준이다(그 상품을 보다가 다른 경로로 전환한 방문은 안 잡힘). 행을 누르면 페이지 분석으로 이동.
- GA4 가 받고 있는 이벤트 목록과 "주요 이벤트" 설정·이커머스 상품 지표(상품 이벤트가 있을 때만)는 카드 아래 접힌 영역에 있다. GA4 관리 → 이벤트에서 견적·주문 이벤트를 "주요 이벤트"로 표시하면 매체별 수치가 거기에도 나온다.

### 2) 페이지 분석 (특정 페이지 따로 보기)
- 왼쪽 메뉴 **페이지 분석** (또는 인기 페이지·인기 상품 행 클릭). 경로·주소 일부·상품번호(`goodsNo=11166`)를 입력하면 그 문구가 들어 있는 **모든 주소를 합쳐** 조회수·방문자·세션·진입·체류, 일별/월별 추이, 유입 매체, 기기, 합쳐진 주소, 발생 이벤트, **그 페이지로 시작한 방문의 전환율**을 보여 준다. 주소는 `#page/검색어/월` 로 공유할 수 있다.
- 데이터는 수집기 웹앱이 GA4 에서 즉시 가져온다(`?mode=page`). 결과는 당월 10분·지난 달 1시간 캐시, 새 조회는 10분에 40회까지(한도·남용 방지). 한 번에 약 10건의 GA4 호출(Core 한도, 실시간 한도와 별개).

### 3) 회사 IP 제외 — GA4 필터 (2026-10-15 확인: 규칙 있음, 필터는 "테스트" 상태)
GA4 는 방문자 IP 를 API 로 내려 주지 않아 **대시보드·수집기에서는 IP 를 걸러낼 수 없고**, GA4 가 수집 단계에서 걸러내야 한다. 적용은 **활성화한 시점 이후 데이터부터**이며 과거 데이터에는 직원 접속이 그대로 남는다(⚠ "의심분 제외" 추정이 계속 필요).
- **이미 설정돼 있음** (스트림 `G-EJ5SHHZPND`): 내부 트래픽 규칙 "사내 IP (견적 처리 PC)" = `traffic_type=internal`, IP `106.254.237.34/32`(이 사무실 PC 의 공인 IP 와 일치). 관리 → 데이터 설정 → 데이터 필터의 "Internal Traffic"(제외)은 **테스트** 상태 — 아직 데이터가 제외되지 않고 `Test data filter name` 으로 표시만 된다.
- **남은 일 (사람이 결정)**: 테스트로 직원 접속만 걸리는지 확인한 뒤 데이터 필터 → Internal Traffic → **활성** 으로 바꾼다. 활성화하면 되돌릴 수 없다(제외된 데이터는 복구 불가). 그날 `config/ga4.json` 의 `internalFilter` 를 `{"state":"active","since":"YYYY-MM-DD"}` 로 바꾸면 대시보드 안내가 바뀐다(`testing`/`pending` 이면 월 화면 맨 위에 "아직 제외되지 않음" 안내가 뜬다).
- 고정 IP 여부는 확인되지 않았다 — IP 가 바뀌면 규칙(`/32`)을 고쳐야 한다. 재택·외근·모바일 접속은 이 규칙으로 걸러지지 않는다. 사무실이 더 있으면 규칙에 IP 를 추가한다.
- **GA4 "주요 이벤트" 설정 주의**: 2026-10-15 현재 `page_view`·`scroll`·`session_start`·`first_visit`·`click` 등 자동 이벤트가 주요 이벤트로 표시돼 있어 GA4 의 주요 이벤트·전환 수치가 부풀려진다. 해제하고 `estimate_complete`(견적 완료)·`홈페이지_견적문의` 등만 표시하는 것을 권장한다. 대시보드의 전환은 이와 무관하게 "전환 화면" 기준이다.

## 공개 범위
- 저장소와 대시보드는 **공개**다 (팀 내부 편의용, 로그인 없음). URL 을 아는 사람은 누구나 방문자·인기 페이지·유입·UTM 캠페인명 집계를 볼 수 있다. 페이지에는 검색 제외(noindex)가 걸려 있다.
- 개인정보·IP·주문/회원 정보는 수집하지 않는다 (GA4 집계 수치만).
- 웹앱 주소는 Secret(`GA4_WEBAPP_URL`)으로 관리하지만, 실시간 조회를 위해 **배포된 페이지 HTML 에는 포함된다**(주소를 아는 사람은 집계 JSON 을 볼 수 있음 — 이미 공개 대시보드와 같은 범위).
- 비공개로 되돌리려면 저장소 Settings → Danger Zone 에서 바꾸되, Pages 는 유료 플랜이 필요하므로 열람 방식을 다시 정해야 한다.

| `scripts/collect.mjs` | 웹앱 JSON 을 받아 월별 파일로 저장 (대체 경로: 서비스 계정으로 GA4 직접 수집) |

## 고도몰 통계 ↔ GA4 수치 차이 (2026-10-14 직접 대조)
고도몰 통계(통계 → 애널리틱스)는 로그인용 일회용 토큰 iframe 이라 API 로 읽을 수 없다. 그래서 **기준은 GA4** 로 하고, 아래처럼 두 통계를 대조해 차이의 성격을 확인했다.

| 항목 | 대조 결과 |
|---|---|
| 인기 상품·카테고리·게시판 순위 (9월) | 순위 거의 동일. 조회수는 상품 ±5%, 카테고리·게시판 GA4 10~20% 높음 |
| 일반 페이지 조회수 (9월, 상위 페이지) | 고도몰의 1.0~1.25배 |
| **`/dbk/dbk_estimate_list.php`** (견적 목록) | **GA4 45,121 vs 고도몰 3,451 (13배)** — 직접 유입·데스크톱 Chrome 100명이 월 42,670뷰(1인당 약 427뷰). 내부 새로고침·자동 접속으로 추정, 고도몰은 이를 제외. 이 한 페이지가 9월 총 페이지뷰 차이(89,093 vs 45,144)의 대부분 |
| 일별 방문자 (10/8~10/14) | 바쁜 날은 거의 같음(10/13: 751 vs 752). 한가한 날은 고도몰이 많음(10/10: 135 vs 58) — GA4 가 못 잡는 기본 방문(봇·미동의·JS 미실행 등)을 고도몰이 더 세는 것으로 보임 |
| 방문 횟수(세션) 7일 합 | 고도몰 2,945 vs GA4 2,753 (0.93배) |

대시보드는 이 차이를 숨기지 않는다: 방문자 대비 조회수가 40배를 넘는 페이지에 ⚠ 와 설명을 붙이고, 하단에 차이의 성격을 적어 둔다. 차이를 더 줄이려면 GA4 관리 → 데이터 스트림 → 내부 트래픽(IP) 필터를 사용자가 직접 설정해야 한다(설정 이후 데이터부터 적용, 되돌리기 어려움).
진단 도구: Apps Script 에디터에서 `diagnose` 를 실행하면 특정 페이지 조회수가 어디서(출처·국가·기기·날짜) 오는지 로그에 나온다.

### 오차가 생기는 이유와 대시보드의 보정
| 원인 | 설명 | 처리 |
|---|---|---|
| ① 방문자를 세는 방식 | 고도몰의 기간 방문자는 **일별 방문자의 합**이다(7일 표시값 2,704 = 692+182+135+124+558+751+262). GA4 기본은 **월 단위 중복 제거**라 같은 사람이 여러 날 오면 더 적다. | 방문자 카드를 **일별 합**으로 표시(고도몰 방식), 중복 제거 값은 "순 방문자"로 병기. 격차 16~19% → 10~15% |
| ② 측정 도구 차이 | GA4 는 방문자 브라우저가 구글 태그를 보내야 기록된다(광고 차단·보안 프로그램·개인정보 보호 브라우저가 막으면 누락, 알려진 봇은 자동 제외). 고도몰은 자체 집계라 접속이 적은 날 더 많이 센다. **(추정, 미검증)** | 보정 불가 — 안내만 |
| ③ 내부 새로고침 | 견적 목록·상세(`/dbk/dbk_estimate_*`)는 방문자 1명당 19~68뷰로, 직원이 열어 둔 화면의 새로고침으로 추정. 고도몰은 이를 제외하는 것으로 보인다. | ⚠ 표시 + 페이지뷰 카드에 "의심분 제외 ≈" 병기. 기준: 조회수 500 초과 & 방문자당 10뷰 초과, 초과분은 방문자당 2뷰(정상 평균 1.8) 기준으로 환산 |
| ④ 집계 시차 | GA4 표준 보고서는 처리 지연으로 최근 값이 나중에 조금 바뀐다. 고도몰도 당일은 집계 중. | 안내 (접속자 패널만 실시간) |

**개선 후 남은 오차 (직접 대조, 2026-08~10)**

| 항목 | GA4 ÷ 고도몰 |
|---|---|
| 방문 횟수(세션) | 0.99 ~ 1.07 |
| 방문자 (일별 합) | 0.85 ~ 0.90 (개선 전 중복 제거 0.81 ~ 0.84) |
| 페이지뷰, 의심분 제외 (9월) | 약 0.97 (개선 전 1.97) |
| 인기 상품·카테고리·게시판 | 순위 거의 동일, 조회수 ±5~20% |

남은 방문자 10~15% 격차는 ②(측정 도구 차이)로 보이며 GA4 설정으로는 줄이기 어렵다. 내부 새로고침을 아예 걸러내려면 GA4 내부 트래픽 필터(IP)를 사용자가 직접 활성화해야 한다(되돌리기 어려움).

### 방문 측정 공백 (2025-08 ~ 2026-07-08) — 사이트가 쉰 것이 아니라 측정이 빠진 것으로 보인다
- GA4 방문자는 이 기간 월 0~78명이고, 고도몰 통계(전체 방문자 수, 최근 1년 월별)도 2025-10 ~ 2026-07 이 모두 0, 2026-08 부터 집계된다.
- 그런데 **고도몰 "회원가입 수"는 같은 기간에 매달 기록**되어 있다(아래 표). 가입이 있었다면 방문도 있었으므로, 이 구간은 "방문이 없던" 것이 아니라 **GA4 태그와 고도몰 방문 통계가 모두 기록하지 못한 구간**일 가능성이 높다. (관리자가 직접 등록·이관한 회원이 섞였을 가능성은 아직 확인하지 못했다.) 원인(공통 헤더·푸터의 측정 코드 누락, 주소·도메인 변경 등)은 데이터만으로 확정할 수 없다.
- 2026-07-09 부터 GA4 가 기록을 재개했고, 고도몰 방문 통계는 2026-08 부터 집계된다.
- 대시보드는 이 달들을 "집계 없음"으로 비활성 처리하고 전월·전년 비교에서 제외한다. 월별 요약표에는 고도몰에서 직접 확인한 가입 수를 *로 참고 표시한다(`data/ref/godomall-signups.json`, 2026-10-14 확인). 신뢰할 수 있는 방문 데이터는 **2025-01~07, 2026-07-09 이후**다.

**고도몰 "회원가입 수" 월별 확인값 (2026-10-14)**

| 월 | 고도몰 | 대시보드(가입 완료 화면 기준) |
|---|---|---|
| 2025-10 ~ 2026-06 | 6 / 15 / 14 / 12 / 19 / 28 / 25 / 20 / 20 | 집계 없음 (측정 누락) |

| 2026-08 | 8 | 6 |

일별 대조(10/8~10/13): 고도몰 1·1·0·0·3·0 = 대시보드 1·1·0·0·3·0 (**완전 일치**). 측정이 정상인 달에는 가입 완료 화면 기준이 고도몰과 0~2명 차이로 맞는다.

**조사 결과 (2026-10-14) — 그 기간 방문 기록은 어디에 남아 있나**

| 확인한 곳 | 결과 |
|---|---|
| GA4 (같은 속성) | 방문 거의 없음. GA4 는 과거 데이터를 사후에 채울 수 없다 |
| GA4 계정의 다른 속성 | `아이티켓 (GA4)`, `itket-keyword-d…`, `on-core` 3개뿐. 이 사이트의 방문이 따로 쌓인 속성은 없음 |
| 고도몰 방문 통계 | 2025-10 ~ 2026-07 이 0 (2025-10 이전은 조회 기간 한계로 미확인) |
| 고도몰 주문통계(월별) | **매달 주문이 있었음**: 2025-12 8건 / 2026-01 9 / 02 8 / 03 14(10,621,000원) / 04 14 / 05 12 / 06 18 / 07 13 / 08 7 / 09 11 / 10 4 |
| 고도몰 회원가입 수 | 매달 6~28명 (위 표) |

| 서버 접속 로그 | SFTP 최상위에 로그 폴더 없음 (NHN커머스에 요청해야 할 수 있음) |

- 결론: **방문 기록은 남아 있지 않다. 반면 주문·가입은 남아 있어 사이트는 운영 중이었다.** 방문 측정만 빠진 구간이다.
- **유력한 단서(미확정)**: 서버 `.htaccess` 가 **2025-07-24** 에 페이지 캐시 규칙(`X-Cache-Key`, `GMCS` 쿠키 조건으로 메인·상품목록·상품상세를 캐시 경로로 처리)을 갖추도록 바뀌었다(이후 2025-11-12 에 캐시 대상 페이지가 늘었고, 2026-03-19 에 SSL 인증 설정이 바뀜). 방문 측정이 끊긴 시점(2025-08)과 맞는다. 캐시로 서비스되는 페이지에서 방문 추적이 실행되지 않았을 가능성이 있으나, GA4 는 브라우저 측정이라 캐시만으로는 설명이 부족해 **확정할 수 없다.** 상단 "속도개선관리"(페이지 캐시) 설정의 변경 이력과 대조해 볼 가치가 있다.
- 다른 곳에 남아 있을 수 있는 것: **네이버 로그분석**(공통 헤더에 `wcs` 코드 설치됨, 사이트 ID `2503cac31ee67a0`)의 2025-08 ~ 2026-06 방문 기록, NHN커머스의 서버 접속 로그.
- 별도 점검 권장(보안): SFTP 최상위(웹 루트)에 무작위 이름의 압축 파일 2개(`RcYiVLeZxs.tar.gz`, `xyLtYLuaCh.tar.gz`, 각 약 493KB, 2026-02-25)와 2021년의 `dataQuery.sql`(약 22MB)이 있다. 내용은 열어 보지 않았다. 외부에서 내려받을 수 있는 위치라면 노출 위험이 있으니 용도를 확인하고 필요하면 삭제한다.

## GA4 API 한도(쿼터) 관리
GA4 Data API 는 **프로젝트·속성당 시간당 14,000토큰**(일 200,000) 한도가 있고, **실시간(Realtime)·일반(Core) 한도가 따로** 있다. 요청 비용은 행 수·차원 수·필터·기간에 따라 달라진다. 2026-10-14 에 실시간 한도가 소진되어 패널이 멈춘 적이 있어 다음처럼 막아 둔다.

| 장치 | 내용 |
|---|---|
| 서버 캐시 | 접속자가 아무리 많아도 실시간 API 는 단계별 캐시 시간(30초/3분/10분)에 한 번만 호출 |
| **남은 토큰 기반 자동 조절** | 응답의 `remaining` 으로 캐시 시간을 늘림: 접속자 수 간격 — 남은 9,000 초과 30초 / 6,500 초과 60초 / 4,000 초과 120초 / 2,000 초과 300초 / 이하 900초 (페이지·그래프, 기기 구분은 그 6배·20배 이상으로 함께 늘어남) |
| 호출 수 감소 | **3단 갱신**: 접속자 수(1회)만 30초마다, 지금 보는 페이지+분당 그래프(2회)는 3분마다, 기기 구분(1회)은 10분마다 |
| 한도 오류 대응 | 오류 즉시 5분간 API 를 쉬고, 마지막 성공 값을 "N분 전 값"으로 표시 |
| **방치된 탭 자동 정지** | 15분 조작이 없으면 화면이 실시간 갱신을 멈춤(조작하면 재개). 열어 둔 탭이 한도를 계속 쓰는 것을 막는다 |
| 수집(Core) | 30분마다 당월만, 무거운 인기 항목 조회는 2시간에 1번. 한도 오류는 조용히 건너뛰고 다음에 재시도 |

**갱신 간격을 이렇게 정한 이유 (2026-10-14 실측 기준)**

실측: GA4 실시간 호출은 **1건당 20~55토큰**(내용보다 호출 수가 비용을 정한다. 접속자 수 18~34, 페이지 목록 약 36~55). 수집(Core)은 1토큰 수준(시간당 약 210). 한도는 실시간 14,000 / 시간. 표는 한 사람이 탭을 계속 열어 두는 최악의 경우(시간당)다.

| 단계 | 내용 | 간격 | 호출/비용 | 한도 사용 |
|---|---|---|---|---|
| ① 접속자 수 | "지금 접속 중 N명" — 화면에서 가장 중요한 숫자 | **30초** | 1회 / 약 22 (18~32) | 약 2,640 |
| ② 페이지·그래프 | 지금 보는 페이지, 분당 접속자 그래프 | 3분 | 2회 / 약 100 | 약 2,000 |
| ③ 기기 구분 | PC·모바일·태블릿 | 10분 | 1회 / 약 20~35 | 약 200 |
| 합계 | | | | **약 4,850 (35%)** |
| 당월 수치(화면) | 저장된 파일을 읽음(GA4 한도 안 씀) | 5분 | | 0 |
| 수집(Core) | GA4 표준 보고서는 원래 수 분~수 시간 늦게 반영 → 더 짧게 해도 이득 없음, Apps Script 트리거 실행 시간(일 90분) 한도도 있음 | 30분 | | 약 1.5% |

- **실시간 "느낌"은 간격보다 화면 효과가 크다**: 15초마다 서버를 확인해 새 측정이 있으면 즉시 반영, "N초 전"을 1초마다 올리고, 숫자가 바뀌면 ▲▼ 변화와 강조 애니메이션을 보여 준다. 이 효과들은 한도를 쓰지 않는다.
- 35%는 24시간 내내 켜 둔 최악의 경우다(실측 2026-10-14: 접속자 수 18~32토큰, 3분 단계 약 100토큰). 남은 토큰이 9,000 아래로 내려가면 간격이 자동으로 늘어 40% 안팎에서 균형을 잡는다(사람이 하루 몇 시간 보는 일반적인 사용은 몇 % 수준).
- "합계 행(TOTAL)"으로 접속자 수와 페이지 목록을 한 번에 받는 방법은 쓰지 않는다: 합계가 중복(여러 페이지를 본 사람)을 포함해 실제 접속자와 다르다(실측 49 vs 43).

**상태 확인:** 웹앱 주소에 `?mode=live` 를 붙여 열면 `budget` 항목에 이번 갱신 비용(`cost`), 남은 토큰(`remaining`), 다음 갱신까지 초(`ttl`)가 나온다. `remaining` 이 계속 2,500 아래면 간격이 늘어난 상태다.
**주의:** 테스트로 대시보드를 연 브라우저·자동화 도구(Playwright 등)를 닫지 않으면 계속 한도를 쓴다. 한도가 소진되면 보통 1시간 안에 회복된다.

## 알아둘 점
- GA4 수치는 고도몰 애널리틱스와 정의·집계 방식이 달라 **값이 일치하지 않는다.** 앞으로의 기준은 GA4 (위 표 참고).
- **회원가입**: 이 사이트는 가입 완료 시 GA4 `sign_up` 이벤트를 보내지 않는다(2025년부터 0건 — 2026-10-14 확인). 그래서 **가입 완료 화면(`/member/join_ok.php`)을 본 사용자 수**(일별)를 가입 수로 쓴다. 나중에 사이트가 `sign_up` 이벤트를 보내기 시작하면 그 달부터 이벤트를 우선 사용한다(이중 집계 없음). 같은 사용자가 같은 날 완료 화면을 새로고침해도 1로 센다. 화면에는 "가입 완료 화면 기준"으로 표시된다.
  - 과거 월은 Apps Script 에서 `backfillSignups` 를 한 번 실행하면 채워진다.
- 방문자(활성 사용자)는 월마다 중복 제거한 값이라 월을 더해도 연 방문자가 되지 않는다. 연간 화면은 이를 합산하지 않는다.
- 로컬 확인(가짜 데이터): `yarn mock` → `.sample/site/index.html` (저장소에는 올라가지 않음)
